# AIFlow：个人 AI 工作流平台设计草案

状态：待确认。本文中的技术和范围是建议，不代表已实现或经过生产验证。

## 目标与产品定位

面向个人开发者构建可自部署的 AI 工作流平台：通过画布配置流程，调用模型和知识库，查看每一步的结果，并将发布版本作为 API 调用。以“内部知识问答与信息处理”为首个演示场景，贯通需求、开发、部署、评估与迭代。项目应能独立运行、展示真实执行记录，并能解释架构取舍与局限。

首版不追求复刻 Coze 或 Dify 的全部能力、插件市场、多租户商业化、复杂多智能体、任意代码执行或高可用集群。先做可验证的纵向闭环，再按实际需要扩展。

## 调研与参考

- Coze Studio 将可视化工作流、智能体、工具和知识能力组合起来；其工作流以 DAG 表达控制流和数据流。参考其节点能力和调试体验，不照搬微服务规模。[Coze Studio](https://github.com/coze-dev/coze-studio)、[节点开发说明](https://github.com/coze-dev/coze-studio/wiki/11.-Add-new-workflow-node-types-%28backend%29)
- Dify 将工作流、模型、工具、知识检索整合为应用平台；参考其工作流和 RAG 的产品闭环。[Dify](https://github.com/langgenius/dify)
- 本地参考项目采用 pnpm/Turbo、Next.js、NestJS、独立 AI 引擎，已将图构建、节点注册、校验和变量解析拆开。其源码头注明不可开源；仅借鉴通用设计思路，独立设计和实现，发布前自行核对素材及依赖许可。
- 本地参考图构建器通过排除未选分支的子树处理条件分支；分支汇合时共享后继可能被误排除。新实现应明确定义边状态和汇合规则，以菱形图测试验证。

## 方案与取舍

1. **推荐：全 TypeScript 模块化单体 + 独立引擎包。** React/Vite 前端、NestJS API、PostgreSQL；pnpm workspace + Turbo 管理两个部署单元及有实际消费者的共享包。统一语言便于个人交付；AI 生态的一些 Python 专属工具接入成本较高。
2. **TypeScript 前端 + Python 后端。** AI 生态丰富，但需要维护两套工具链、契约与部署；适合明确依赖 Python 算法或已有 Python 经验的情况。
3. **基于现成平台二次开发。** 可更快交付业务，但核心执行机制的自主设计与面试讨论空间较小，升级也受上游影响。

当前建议方案 1。Vite 适合主要为登录后交互的工作台；如后续需要大量服务端渲染或公开 SEO 页面，再重新评估。工作流首版采用自己实现的受限 DAG 执行器；模型通过适配器接入兼容 OpenAI API 的服务，不提前绑定特定厂商或框架。具体依赖版本在初始化时核对兼容性并锁定。

## 目标结构

```text
apps/web/                 工作台、画布、运行记录
apps/api/                 身份、工作流、执行、知识库和发布 API
packages/workflow-engine/ 图校验、调度、变量、节点执行接口
packages/contracts/       前后端共用的工作流和 API 契约
docs/                     需求、设计、决策、测试、部署和复盘
```

依赖方向为应用到共享包，引擎不依赖 NestJS 或浏览器。只在有真实消费者时创建包；目录可以随实现调整。PostgreSQL 持久化定义、版本和运行记录；首版同步或进程内异步执行，进程重启时未完成运行标记为中断，不承诺恢复。执行接口与存储分离，后续再引入队列和独立 worker。

## 核心领域与执行语义

- Workflow 是可编辑草稿；WorkflowVersion 是发布时不可变快照；Run 固定关联执行快照；NodeRun 记录节点状态、耗时和安全处理后的输入输出。
- JSON 工作流定义包含 schemaVersion、节点、端口、边和变量引用；客户端和服务端均校验，服务端为最终裁决者。发布要求节点 ID 唯一、端口与边合法、可达、无环、变量类型兼容且配置完整。
- 首版节点：开始、结束、LLM、条件、知识检索。按依赖就绪顺序执行，未选中的边标记 skipped；汇合节点在所有入边都已决议且至少一条有效时执行。节点和运行具有 pending、running、succeeded、failed、skipped、cancelled 等明确状态；失败、超时、取消均有可见结果。初期不支持循环和并行执行。
- 边决议递归传播：所有入边均 skipped 的节点跳过并将出边标记 skipped；汇合节点不能读取未执行分支的必填输出，校验阶段拒绝这类引用，确有需要时通过显式可选值和默认值表达。首版节点失败即终止运行，未运行节点标记 skipped；取消中止可取消的外部请求并标记剩余节点。运行记录写入完整草稿快照；启动时将属于已退出实例的 running 记录标记为 interrupted。SSE 首版不保证事件重放，断线后查询运行详情；取消使用独立 API，以最终持久化状态为准。
- 草稿调试与发布调用均固定快照；运行事件提供开始、节点状态、结束和错误，通过 SSE 推送，断线后可查询持久化结果。服务端设置超时和步数限制；外部调用的重试只对明确安全的操作开启。
- API 密钥和模型凭据不返回明文；日志脱敏。知识文档上传限制大小和类型，检索结果带来源。所有 API 做身份及资源归属检查。部署时使用 HTTPS、环境变量注入密钥、备份和恢复演练。

## 交付阶段与验收

1. **需求与基线**：明确目标用户、首个场景和验收样例；建立仓库、工程脚本、CI 和架构决策记录。干净环境可安装、检查、构建。
2. **流程最小闭环**：工作流 CRUD、画布、开始/结束节点、保存和运行；刷新后数据仍在，非法图无法运行。
3. **模型与调试**：模型配置、LLM/条件节点、变量引用、SSE 与运行详情；菱形分支汇合、错误与超时均可复现且结果正确。
4. **知识问答**：文档入库、切分、向量化、检索及来源展示；准备固定问题集，记录命中、回答质量、延迟与失败案例。向量存储优先评估 PostgreSQL + pgvector，验证本地部署与迁移可行性后确定。
5. **发布和调用**：草稿发布为不可变版本，API 密钥调用并记录版本；修改草稿不影响已发布版本。
6. **上线与复盘**：Docker Compose 单机部署、域名和 HTTPS、数据库备份恢复、日志与健康检查；端到端冒烟测试、故障演练、成本与限制说明、演示视频和架构决策记录。
7. **受限智能体扩展**：在闭环稳定后引入单智能体工具调用，先提供只读工具和明确的最大轮次、超时、调用预算及执行轨迹；验证模型选择工具、参数校验和失败处理。固定 DAG 并不等同于自主智能体，此阶段完成前不宣称已实现智能体规划能力。

每阶段先写可验收的故事和测试，再实现、验证、记录；前一阶段未通过不扩大范围。实际工期按每周可投入时间估算，不预设虚假日期。

## 测试、观测与面试材料

针对图校验、变量解析、条件分支与汇合、状态机编写单元测试；针对数据库、模型适配器和 API 做集成测试；覆盖一次从编辑、发布到调用的端到端流程。模型测试使用可控替身，另保留明确标注成本和波动的真实模型冒烟测试。记录运行成功率、节点耗时、模型调用次数与 token 用量；避免将用户敏感内容作为默认日志。

保留需求背景、方案比较、决策及变更原因、架构图、故障记录、测试报告、部署说明和真实指标。简历只写实际完成与测量过的结果；重点准备 DAG 调度、分支汇合、版本一致性、RAG 评估、流式事件与单机可靠性等问题。

## 待确认事项

上述首个场景、全 TypeScript 方案与首版范围为建议。首版建议单用户账号登录、部署于一台 Linux 主机；身份实现及部署供应商在实施计划中结合环境确定。确认设计后再根据实际开发环境生成工程基线和详细实施计划；技术选择和阶段范围可以调整。
